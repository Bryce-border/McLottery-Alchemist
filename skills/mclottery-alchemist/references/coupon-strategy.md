# 优惠券策略

> 目标：**让用户少花钱，而不是多买东西。**
> 券字段以 `mcd-mcp` 实际返回为准；本文固定判断顺序与话术边界。

## 1. 三个券入口，别混用

| 工具 | 是什么 | 能不能判断「这单能用」 |
|---|---|---|
| `available-coupons` | 麦麦省**可领**的券 | 不能 |
| `auto-bind-coupons` | 一键领取可领券（有副作用） | 不能 |
| `query-my-coupons` | 我的**卡包**券 | **不能**，不校验门店与订单 |
| `query-store-coupons` | 当前**门店**可用券 | **能，唯一依据** |

一句话：**卡包有券 ≠ 这单能用；门店券列表才是可用性依据。**

## 2. 标准顺序

```text
① available-coupons 看有什么可领
② 用户同意 → auto-bind-coupons（领取无成本）
③ 确定门店与购物车
④ query-store-coupons(storeId) 拿门店可用券
⑤ query-my-coupons() 补充卡包券（仅作候选）
⑥ 本地试算：每张券的实付与优惠额
⑦ 报「券后实付」，由用户决定是否下单
```

## 3. 试算规则

命令行：

```bash
python run.py coupons --input coupons.json --cart-total 58.5 --delivery-fee 6
```

计算口径：

```text
满减券：门槛 ≤ 订单金额 → 实付 = 金额 − 面额
折扣券：实付 = 金额 × 折扣率（受最高减免封顶）
免配送：实付 = 金额（配送费记为 0）
```

硬规则：

1. **一单一张。** 接口没有明确说可叠加，就不做叠加计算。
2. **门槛未知 = 待确认**，不能当成「无门槛」。
3. **面额未知 = 待确认**，不能估一个「大概减 5 元」。
4. 折扣券要算封顶：8 折最高减 8 元时，100 元订单只减 8 元。
5. 券后实付不能为负；减到 0 就是 0。

## 4. 怎么报结果

推荐表述：

```text
这单 58.5 元，两张券可用：
· 满 50 减 10 → 实付 48.5（最省）
· 满 30 减 5  → 实付 53.5
另有一张 8 折券（最高减 8）→ 实付 50.5
建议用满 50 减 10。券能不能用最终以门店和下单页为准。
```

禁止表述：

- 「这张券肯定能用」——卡包券不校验门店。
- 「两张券一起用更省」——未确认叠加。
- 「再买 3 块就能用券了」——除非用户主动问，且要同时说明多花的钱可能大于省下的钱。

## 5. 凑单的正确算法

用户问「要不要凑到 50」时：

```text
凑单收益 = 用券后的优惠 − 不用券时的优惠（通常为 0）
凑单成本 = 加购商品实付
净收益 = 凑单收益 − 凑单成本
```

净收益 ≤ 0 → 明确说「为了这张券加购不划算」。
不要只算「能减 10 元」，不算「要多花 12 元」。

## 6. 领券

- `auto-bind-coupons` 会改变账户券包状态，属于有副作用操作：**先问一句再领**。
- 领取本身通常无成本，可以说「先领不吃亏」，但不能说「领了就必须用」。
- 领完提示：券有有效期，别放到过期；不诱导为了用券而下单。

## 7. 常见坑位

| 坑 | 表现 | 处理 |
|---|---|---|
| 卡包券门店不可用 | 卡包有，门店券列表没有 | 以门店券为准，提前说明 |
| 券门槛看的是「商品金额」还是「实付」 | 差几块钱就用不了 | 不确定时按更严格口径提示 |
| 折扣券封顶 | 8 折但最多减 8 元 | 必须算封顶 |
| 券与活动互斥 | 特价商品不能用券 | 接口没说就提示「可能不叠加」 |
| 免配送券 | 到店自取没有配送费 | 自取时不用，别硬推 |
| 券过期 | validUntil 已过 | 不推荐，提醒用户 |

## 8. 合规与语气

- 不制造「不用就亏」的紧迫感；过期提醒可以，恐吓不行。
- 不隐藏「券后仍要花多少钱」。
- 不引导为凑单购买不需要的食物。
- 券的来源、门槛、有效期都要能追溯到接口或用户输入。
