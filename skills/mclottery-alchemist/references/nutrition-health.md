# 营养与热量管理

> 只做「按热量和营养数据搭配一餐」的算术，不做医疗、减重、疾病饮食建议。
> 数据来源：`list-nutrition-foods`。

## 1. 数据口径（TOON 格式）

`list-nutrition-foods` 无入参，返回的 `data` 是**字符串**，不是 JSON 数组：

```text
[2]{productName,nutritionDescription,energyKj,energyKcal,protein,fat,carbohydrate,sodium,calcium}:
  猪柳麦满分,null,1288,308,16,16,24,781,213
  巨无霸,null,2300,550,25,30,40,900,120
```

- 表头 `[N]{列名}`，随后 N 行逗号分隔，`null` 表示缺值。
- **优先用 `energyKcal`**；只有 `energyKj` 时除以 4.184，并标注「由 kJ 换算」。
- 份量口径以接口为准；接口没给就标「按接口默认份」，不要自行换算成 100g。
- 字段缺失（没有热量）→ 该餐品**不参与计算**，但必须告诉用户「这几个没算进来」。
- 不把「同类餐品」的热量套到缺数据的餐品上。

命令行：

```bash
python run.py nutrition --input nutrition_toon.json --target 700
```

## 2. 用户给目标热量时

```bash
python run.py nutrition --input nutrition.json --target 700
```

组合规则：

1. 候选为当前菜单中**有热量数据**的餐品。
2. 组合 1–3 件（默认 3），选总热量最接近目标的方案。
3. 优先不过量：同样接近时，选不超目标的组合。
4. 偏差超过目标 10% 时明说「当前菜单没有更合适的组合」。
5. 输出：餐品清单、总热量、蛋白质/脂肪/碳水/钠、偏差、未参与计算的餐品。

推荐表述：

```text
按 700 kcal 目标，最接近的组合是：
巨无霸 + 中杯可乐 = 700 kcal（偏差 0）
蛋白质 25g｜脂肪 30g｜碳水 78g｜钠 910mg
另有 1 个餐品因缺少热量字段未参与计算：麦旋风。
这是按接口默认份算的，实际以门店份量为准。
```

## 3. 用户没给目标热量时

不要擅自替用户定 1200 kcal 这类数字。可以：

- 问一句「你今天想控制在多少 kcal 左右」；
- 或先给单品的营养数据，让用户自己选。

例外：用户明确说「按 500 大卡配一餐」，那就按 500 算。

## 4. 一天摄入评估

```bash
python run.py nutrition --input today.json --target 1800
```

- 只累加用户实际点/吃的餐品，不假设三餐结构。
- 输出「低于目标 / 接近目标 / 超出目标」+ 剩余热量。
- 钠超过 2000mg 时给一句提示，不展开成医学结论。

## 5. 边界（必须遵守）

不能做：

- 诊断肥胖、营养不良、代谢疾病；
- 承诺「这样吃能瘦 X 斤」；
- 给孕妇、儿童、老人、慢病人群定制治疗性饮食；
- 建议用代餐/跳餐替代正常饮食；
- 把热量数字说成「精确值」——它有接口与份量误差。

可以说：

- 「按接口数据，这一餐约 X kcal」；
- 「如果目标是控制总热量，可以把中薯换成小薯/沙拉，热量会低一些」；
- 「特殊人群或治疗性饮食，建议咨询营养师或医生」。

## 6. 与点餐、积分的联动

- **点餐时**：用户说「想吃得轻一点」，先查营养数据再推荐，不凭印象说「沙拉最低」。
- **积分计划时**：计划表里的餐品搭配要参考热量，不能为了攒积分建议高频高热量组合。
- **不要**为了积分推荐「多点一份」；需要凑金额时优先推荐可保存/可分享的组合，并如实说明热量。
